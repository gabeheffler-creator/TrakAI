PRIORITY 1 — Program review gate (coach approval before client sees it)
===========================================================

THE PROBLEM
Today, in artifacts/trak-coach/src/pages/client-profile.tsx (around 
lines 942-954), assigning a program — including an AI-generated one — 
makes it immediately live for the client. There is no point where a 
coach reviews or approves what the AI produced before a client receives 
it. A coach's name and judgment are effectively attached to programming 
they may never have actually looked at.

THE GOAL
No program reaches a client without a coach explicitly confirming it, 
every time — whether the program was built by hand or generated by AI. 
AI-generated programs in particular must land in a reviewable draft 
state, not an assigned one.

WHAT THIS SHOULD LOOK LIKE
- When a program is generated via POST /api/programs/generate-ai, it is 
  created but not assigned to any client and not visible to any client.
- The coach lands on a review view showing the full generated structure 
  (phases, days, exercises) using the same editing tools already used 
  for manually built programs, so they can adjust anything before it 
  goes further.
- The coach takes an explicit action — something like "Approve & Assign" 
  — before it becomes visible to a client. This should feel like a 
  deliberate step, not a formality that's easy to click through blindly 
  (e.g. don't make it the same button as "save draft").
- This same protection should apply to the existing manual assignment 
  flow too: assigning any program to a client should always be an 
  explicit, confirmed action — audit whether the current flow already 
  does this adequately for manually-built programs, and only change it 
  if it doesn't.
- A client must never be able to fetch or see a program that hasn't 
  passed this step, even by directly hitting an API route — enforce this 
  server-side, not just by hiding it in the UI.

PRIORITY 2 — Centralized AI client, rate limiting, and error visibility
===========================================================

THE PROBLEM
Three routes call an AI provider directly and independently: 
POST /api/programs/generate-ai, GET /api/clients/:clientId/tasks/:taskId/
ai-alternatives, and POST /api/nutrition/extract. None of them share 
infrastructure. There's no rate limiting anywhere in the API. And 
critically, when /api/nutrition/extract fails, the error is swallowed 
silently in artifacts/trak-client/src/pages/nutrition.tsx (lines 
323-346) — the user just sees nothing happen, with no indication 
anything went wrong.

THE GOAL
One shared, well-behaved gateway for every AI call in the app, so cost, 
failure, and abuse are handled consistently instead of three times over 
— and a user should never be left wondering if the app is broken.

WHAT THIS SHOULD LOOK LIKE
- A single shared module that all three existing AI call sites route 
  through, rather than each hitting the provider independently. Model/
  provider and API key should be configurable via environment variables, 
  not hardcoded per feature.
- Every AI call is logged somewhere queryable (who called it, when, 
  which feature, success/failure) so cost and usage are auditable later 
  without having to add this after the fact.
- Rate limiting on the API generally, with tighter limits specifically 
  on: authentication endpoints (login/signup/reset — protect against 
  credential stuffing) and the three AI endpoints (protect against cost 
  blowouts). Limits should be configurable, not hardcoded magic numbers.
- Per-user usage caps on the AI endpoints specifically (e.g. a sane daily 
  limit on nutrition extraction calls per client) — separate from the 
  rate limiter, since this is about cost control, not just abuse 
  prevention.
- When any AI call fails for any reason — timeout, provider error, rate 
  limit hit — the user gets a real, visible message explaining that it 
  failed and what they can do next (retry, or enter it manually). Fix 
  the specific silent failure in nutrition.tsx as part of this; audit 
  the other two call sites for the same problem and fix them too if 
  found.
- A sensible timeout on all three calls so a slow provider response 
  doesn't leave a user staring at a frozen loading state indefinitely.

PRIORITY 3 — Cross-device auth (web + native mobile, same account)
===========================================================

THE PROBLEM
The current auth (express-session, httpOnly cookies, bcrypt, role-
separated middleware) is solid for the web apps, but cookies don't carry 
cleanly into a native mobile shell once the mobile apps stop being iframe 
wrappers. There's also no multi-session visibility, no password reset, 
and no self-serve way for a client to join a coach's roster other than 
however the seed data currently links them.

THE GOAL
The same coach or client account should work identically whether they're 
on the web app or a native mobile app, including being logged in on both 
at once, without weakening the security of the existing cookie-based web 
session.

WHAT THIS SHOULD LOOK LIKE
- Keep the existing cookie-based session for the web apps as-is — it's 
  working well. Add a second, token-based path (e.g. issued JWT/refresh 
  token pair) for native mobile clients, backed by the same underlying 
  user/auth logic, so there's one source of truth for "is this user 
  authenticated," just two ways of proving it depending on the client.
- A user can be logged in on their phone and their laptop simultaneously 
  without either session interfering with the other.
- Settings should let a user see their active sessions/devices and revoke 
  one remotely (e.g. "log out everywhere").
- Add password reset via emailed token, and basic email verification on 
  signup.
- Add a coach-invites-client flow: a coach enters a prospective client's 
  email, the system generates a signup link tied to that coach, and 
  completing signup through that link links the new client to the coach 
  automatically — replacing however this linkage currently only exists 
  via seed data.
- Keep demo accounts (coach/alex/sam/jordan) functioning for local 
  development only, clearly gated so they're not a reachable login path 
  in a deployed environment.

PRIORITY 4 — Close the remaining human-override gaps
===========================================================

THE PROBLEM
Sleep-based automatic workout volume reduction has no override — a 
coach can't restore full volume for a client who reports feeling fine 
despite poor sleep (artifacts/trak-client/src/pages/workout.tsx, around 
lines 1456-1492). Separately, program-builder's editing controls for 
individual days and exercises are incomplete (artifacts/trak-coach/src/
pages/program-builder.tsx, around lines 443-482 and 799-925).

THE GOAL
Anything the app decides automatically — whether by simple logic (sleep 
adjustment) or by AI — should be visibly overridable by a human, 
consistently, everywhere it happens.

WHAT THIS SHOULD LOOK LIKE
- When the app auto-reduces workout volume due to poor sleep, this is 
  clearly labeled as automatic, and the coach (or, if appropriate, the 
  client in the moment) has a straightforward way to restore the 
  original volume for that specific session.
- Fill in the missing edit controls in program-builder for day- and 
  exercise-level fields so coaches have full manual control over 
  anything the AI (or they) built, matching the editing depth already 
  available elsewhere in the builder.
- As you go, if you find any other auto-computed value in the app 
  without an obvious edit path, flag it in your summary even if you 
  don't fix it — I want a running list, not just silent gaps.

PRIORITY 5 — Native mobile shell (separate track, do last)
===========================================================

THE PROBLEM
/trak-client-mobile and /trak-coach-mobile are iframe wrappers of the 
web apps with a cosmetic ?mobile=1 flag — no native lifecycle, no real 
push notifications (currently leaning on browser service-worker push, 
which won't function properly once this needs to behave like a real App 
Store app), and no deep linking.

THE GOAL
A real native iOS shell around the existing apps, so it qualifies as an 
actual app for App Store review rather than a repackaged website, and so 
push notifications and session handling work the way users expect from 
a native app.

WHAT THIS SHOULD LOOK LIKE
- Evaluate and set up Capacitor as the native wrapper for both the coach 
  and client apps, replacing the iframe approach.
- Native push notifications for messages and tasks, replacing the 
  browser service-worker approach.
- The native shell uses the token-based auth path from Priority 3, with 
  the token stored in native secure storage (Keychain), not browser 
  storage.
- Basic deep linking so a push notification tap can open directly to the 
  relevant screen (e.g. a new message opens the conversation).
- This is the largest, most exploratory workstream — if you hit a wall 
  or need a product decision (e.g. Capacitor plugin choice, whether both 
  apps share one Capacitor project or two), stop and flag it rather than 
  guessing.
